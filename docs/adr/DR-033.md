## Decision

`POST /api/response/actions` requires `incident_id`, `action_type` and a
structured `target`, with optional `params`, `mode` and `ttl_seconds`. The
catalog supplies level and the only allowed target/parameter schema; clients
cannot choose a connector, command, level or initial status. Single-mode L0,
L1 and L3 infer their mode; L2 must explicitly choose `automatic` or `manual`.
L2 defaults to 3,600 seconds and cannot exceed the configured maximum or the
hard 86,400-second ceiling. Non-L2 TTLs are rejected. `INCIDENT_MAX_TEXT_CHARS`
also bounds response strings and decision reasons; nested request structures
are bounded and unknown fields are refused. Every request must refer to an
existing incident. Live safeguards are checked before persistence; a new
automatic request is refused while the switch is engaged, whereas automation
already queued before engagement pauses and recovers later.

All active legacy roles may request and list actions in the shared tenant;
only senior/admin can approve, reject or request a rollback. The deciding or
rollback operator is revalidated under a user lock in the write transaction,
and a decision is checked again by the execution worker. L3 and manual L2
require a distinct senior/admin approver; self-rejection remains permitted for
an otherwise eligible user. Missing IDs return 404 only after authorization,
invalid payloads/safeguards 422, illegal state/switch conflicts 409, and
self-approval or insufficient role 403. Lists use bounded descending keyset
pagination and an optional incident filter; action IDs are not ownership scopes
in this shared-tenant baseline. No detail-by-ID endpoint is added.

An optional ASCII `Idempotency-Key` is scoped to the requesting user. Migration
006 stores only SHA-256 digests of the key and canonical request and enforces a
unique user/key pair. Same-key, same-request replay returns the current action
with 200; changed data returns 409, and a new action returns 201. Omitted keys
produce independent actions. Keys are retained as long as the action exists,
are not returned or written to activity details, and are not authentication
secrets. No action or approval is executed in HTTP. After commit, publication
is best effort; a broker error does not falsely report that the durable action
was rejected. The configured Beat reconciliation task retries approved actions
and manual rollback requests. A success response says the request was persisted,
not that it has already executed or that broker publication definitely worked.

An authorized manual rollback records its actor and a monotonically distinct
request timestamp on the executed action, plus an activity; it returns 202.
The worker locks and checks the current request, current active senior/admin
operator, current action and reverse safeguards; manual rollback is permitted
while the switch is engaged. If eligibility or safety changed, the worker audits
one refusal for that request and leaves the original action executed. The
refusal is tied to the request timestamp in the append-only activity log;
reconciliation excludes that stale request until a new authorized request
supersedes it. The list reports `rollback_request_status` as pending, refused
or resolved. A TTL rollback racing a manual request can win; row locks and the
unique command phase ensure at most one reverse command. Database/audit failure
rolls the attempt back and can be retried by Beat. A stopped Beat, broker,
worker or database can still delay recovery; a trusted broker and consistent
replica configuration remain operational prerequisites.
