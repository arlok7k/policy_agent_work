# DR-031 — Mandatory L2 TTL and safe rollback

- **Status:** PB3-T07.
- **Owner decisions (verbatim):**
  > - L2 actions have a mandatory TTL with automatic rollback by Celery Beat. Make the default TTL
  >
  >   and its maximum configurable, with safe defaults you propose in a DR.
  >
  > - Kill Switch halts AUTOMATION only (auto L1/L2 execution and TTL jobs); manual human-approved
  >
  >   execution stays possible. Engage/disengage by senior_analyst or admin, always audited.
  >
  > - Connectors are simulated: they write to executed_commands and NEVER perform network I/O.
  >
  >   Add a socket-level test proving no connection is attempted.
- **Owner selections:** **“1 hour default, 24 hours maximum (recommended)”**;
  **“Hard 24-hour ceiling (recommended)”**; **“Every 5 seconds (recommended)”**
  for the configurable sweep cadence; **“Leave executed and retry
  (recommended)”** when a reverse action becomes unsafe.

## Decision

Every independently requested L2 action has a positive integer TTL. The default
is 3,600 seconds and the configured maximum defaults to 86,400 seconds; an
operator may lower either but neither can exceed the hard 24-hour ceiling. A
lowered maximum is also checked by the worker before execution. Invalid or
inconsistent configuration fails startup. TTL starts at the PostgreSQL-clock
time recorded for successful simulated execution, not at request or approval.
The expiration and execution record commit in the same transaction.

Celery Beat publishes a bounded sweep at the shared configurable interval
(default five seconds, 100 actions). The task samples PostgreSQL time; equality
with `ttl_expires_at` is due. It re-locks the switch, action and current rules,
rechecks that the action is executed, L2 and still due, and calls only its
catalog-defined reverse connector. Rollback command and `rolled_back` activity
are atomic and idempotent. No task message can supply the clock. The switch
skips the entire TTL sweep while engaged; overdue actions remain executed and
are retried after disengagement. The schedule is best effort, not an exact
wall-clock guarantee: outages, worker saturation and lock contention delay it.

A reverse command that fails current safeguards is not run. The action stays
executed and is retried later; one refusal activity is recorded per action and
reason rather than on every sweep. Each refusal advances the action's existing
`updated_at`, rotating it behind other due actions so a protected target cannot
starve an entire bounded batch. Rules, switch, command and audit share the same
transaction and failure rolls it back. `firewall_allow` is independently
requestable only when its eventual reverse block is safe at request and
execution; the reverse is checked again at rollback. `release_host` remains
rollback-only, so no autonomous re-isolation is introduced.

The boundary test freezes the job's database-clock accessor around the actual
selection and rollback transaction; production never accepts a caller-supplied
clock. All replicas must share compatible TTL and sweep configuration, and a
live Beat, broker, worker and database are required for eventual rollback.
