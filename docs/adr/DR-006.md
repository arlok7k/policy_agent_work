# DR-006 — Proposed PB1 data model and public security contract

- **Status:** Option A is implemented; owner approval is **to be confirmed**.
  The available session summary records an option A selection but does not
  preserve the exact owner message, so no verbatim approval is quoted here.
- **Why this is blocking:** §3.4 explicitly says host request/response schemas,
  status codes and auth headers are undocumented; PB1-T04 lists fields but not
  key types, role cardinality, or the runtime database principal. Section
  §18.2(3) says not to default a security boundary, data-model contract or
  public API contract. These choices therefore need owner approval even though
  the general greenfield instruction permits minimal decisions for non-blocking
  gaps. Implementation and verification are tracked in the phase progress;
  the owner-approval evidence remains to be confirmed.

## Recommended minimal contract

1. **Host schema:** UUID primary keys; each user has exactly one of the three
   seeded legacy roles, and a unique, case-normalized username. Sessions store
   only token and CSRF digests, user ID, creation, expiry, revocation and
   reauthentication timestamps. API keys store only a digest, lookup prefix,
   owner, creation, expiry and revocation timestamps. `case_activities` stores
   timestamp, username, source IP (nullable for local CLI actions), action,
   target and JSON details; never store credentials or token hashes in details.
   A small PostgreSQL-backed login-throttle table in migration 002 supports
   atomic, multi-worker rate limiting.
2. **Database boundary:** Migrations own the tables; a non-login `hpb_app` role
   receives only the required runtime table/sequence privileges. A separately
   provisioned login inherits it. The role cannot update, delete or truncate
   activities; statement-level triggers also reject those operations, including
   attempts by the table owner. Migrations create or validate the role and fail
   if it has elevated attributes. Startup validates the runtime connection is
   not the table owner or a superuser and lacks the three destructive activity
   privileges. The startup check also refuses schema/database-owner membership
   and schema creation rights. A database administrator who can alter/disable
   triggers remains outside this protection; the later governance audit adds
   external anchoring. Tests that create/drop temporary login roles require the
   separate `TEST_PG_CLUSTER_DISPOSABLE=1` confirmation because roles are
   cluster-wide; the shared `hpb_app` role is never dropped by a downgrade.
3. **Session and CSRF:** Login takes JSON `username` and `password`, returns a
   user principal and issues new host-only `Secure`, `HttpOnly`, `SameSite=Strict`
   session and `Secure`, `SameSite=Strict` readable CSRF cookies. Unsafe requests
   using a session require a matching `X-CSRF-Token`, bound to that session;
   API keys do not fall back to cookie authorization. Session cookies are opaque
   random tokens; only keyed digests are stored. Logout revokes the session;
   reauthentication rechecks the password and stamps its `reauth_at`. `GET
   /api/auth/me` returns the authenticated principal. Logout and reauth return
   204; login and me return 200. Authentication failures are generic 401s,
   missing/bad CSRF is 403, and throttling is 429.
4. **Admin APIs:** `GET /api/users` returns paginated, explicitly allow-listed
   user data; `POST /api/users` creates a user; `PATCH /api/users` carries an
   `id` plus permitted changes. Disabling a user or changing a password revokes
   all their sessions in the same transaction. `GET/POST/DELETE /api/api-keys`
   manage only the calling administrator's own keys; DELETE identifies a key by
   an `id` query parameter. Key secrets are returned once on creation with
   `Cache-Control: no-store`; later responses contain only safe metadata. Keys
   authenticate as service principals, never inherit the owner's administrator
   role, and cannot call admin endpoints. Other owners' key IDs return 404.
5. **Configurable limits:** Require environment configuration for session TTL,
   password minimum/maximum, login failure limit/window and maximum API-key
   TTL, with conservative example values: 8 hours, 14–1024 characters, five
   failures per source and per account per 60 seconds, and 30 days respectively.
   Use the PostgreSQL clock for expiry and limit windows; never bake policy
   thresholds or TTLs into application code. Rate limits use the direct peer IP,
   not untrusted forwarding headers. The future proxy must explicitly establish
   a trusted client-IP boundary rather than silently trusting a header.
6. **Errors and health:** Use RFC 9457 `type`, `title`, `status`, `code` and
   `correlation_id`; return generic external errors, accepting a safe
   caller-provided correlation ID or generating one. `/api/health` returns a
   minimal `{"status":"ok"}` only when the database is reachable and otherwise
   a generic 503 problem response; it does not disclose configuration.

All request models reject extra fields. Passwords use Argon2id; unknown-user
login performs a dummy verification. Successful login always rotates the
session token. Configuration supplies credentials via environment or secret
files; no production keys or passwords are generated by the agent.

## Options and consequences

- **A — Approve the recommended contract:** permits PB1-T04 through T11 to
  proceed; the resulting public API and legacy behavior must later be reviewed
  at the PB4 baseline gate. This is the recommendation.
- **B — Specify changes:** identify the affected numbered items and desired
  alternatives. Work touching those items remains blocked until resolved.
- **C — Stop PB1:** retain the verified PB1-T01–T03 work without implementing
  an unapproved data model or security/API boundary.
