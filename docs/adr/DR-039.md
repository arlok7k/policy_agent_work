# DR-039 — Explicit trusted-proxy client attribution (PB4-FU01)

- **Status:** Implemented; subject to the PB4 baseline gate.
- **Context:** Direct clients can forge forwarded headers, but the proxy's real
  client address must drive login throttles and audit attribution. The owner
  selected **“Explicit proxy IP (recommended)”**.
- **Decision:** `TRUSTED_PROXY_IPS` is an optional comma-separated list of
  exact IP addresses (no CIDRs, wildcards, duplicates, scoped, unspecified or
  multicast addresses); empty means trust no proxy. Only a matching socket peer
  may supply one valid `X-Forwarded-For` address. Missing, repeated, malformed
  or multi-hop values from a trusted peer fail closed. Direct untrusted clients'
  forwarded headers are ignored. Nginx must overwrite rather than append this
  header, and the ASGI server must not perform its own proxy-header rewriting.
  Compose will assign Nginx a dedicated configured address.
- **Reason:** A single trusted hop, fixed at the network boundary, preserves the
  real source IP without accepting attacker-provided chains.
- **Alternatives:** Trust all private networks; accept the leftmost or rightmost
  address from arbitrary chains; treat every client as the proxy. These enable
  spoofing or collapse attribution and throttling.
- **Consequences:** Operators must configure both the explicit proxy address
  and proxy overwrite behavior consistently. Adding another proxy requires a
  separately reviewed trust arrangement. Direct and trusted-peer spoofing and
  IP-bound audit/throttle paths are covered by integration tests; the local
  mock-upstream Nginx check verified header overwrite. Real Compose HTTP traffic
  passed the browser smoke in CI run 45632988120, which does not itself claim a
  separate end-to-end spoofed-header attribution assertion.
