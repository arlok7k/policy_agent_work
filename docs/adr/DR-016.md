# DR-016 — Signed PB2 webhooks, replay protection and task transport

- **Status:** Implementing PB2-T02/T03; the Redis replay-state durability limit
  below remains an operational risk for the PB4 deployment review.
- **Owner selection:** For the replay question the owner selected the option
  labelled **“Reject replay (recommended)”**. Its description specified signed
  timestamp and UUID event-ID headers, Redis reservations, fail-closed cache
  errors and PostgreSQL fingerprint deduplication, with Redis state-loss risk.
  This is the literal option label, not a reconstructed message.
- **Context:** PB2 requires an HMAC-SHA256 webhook, a payload cap, generic
  rejection, logging, Celery delivery, replay tests and a service initiator;
  the signature wire format and replay behavior were unspecified.

## Decision

1. Require exactly one each of `X-Webhook-Timestamp` (Unix seconds),
   `X-Webhook-Id` (UUID), and `X-Webhook-Signature` (`sha256=` followed by
   lowercase hexadecimal). Sign the exact bytes
   `timestamp + "." + canonical-lowercase-UUID + "." + raw-request-body` using
   HMAC-SHA256. Compare the decoded signature in constant time. The timestamp
   must be within the configured symmetric clock-skew window. The webhook
   signing value is read only from an operator-provisioned Docker-secret file,
   never from an inline environment variable; it must be at least 32 bytes.
2. Read the request as a stream with a configured byte cap, verify the signature
   before JSON/schema validation, and use generic problems: 401 for missing,
   malformed, stale or invalid authentication; 400 for invalid JSON/schema; 413
   for an oversized body; 409 for a replay; and 503 for unavailable replay
   storage or task publication. Log the attempt using the existing allow-listed
   request logger, without request bodies, authentication headers or secrets.
   Invalid/oversized input has no Redis, broker or database side effects.
3. Only after validation, reserve the event UUID atomically in the Redis cache
   with `SET NX` for `2 * configured_skew + 1` seconds, covering the entire
   remaining validity of any accepted timestamp. A reused UUID is rejected even
   when its body differs. If Redis is unavailable, fail closed. Publish the
   normalized-payload task to the `default` queue with an operator-configured
   service initiator header. If publication fails, keep the reservation because
   delivery might have succeeded despite an ambiguous transport failure.
4. Celery 5.7.0 and Redis Python client 8.1.0 are pinned in the hash lock. The
   already-selected Redis server version remains 8.2.11 (DR-001); broker and
   cache use separately configured Redis instances. PostgreSQL's unique alert
   fingerprint is a second, durable defense against duplicate stored alerts.
5. The webhook accepts `source`, `rule_id`, `severity`, optional `agent`,
   `src_ip`/`dst_ip`, and a `raw` JSON object. String length, body size, clock
   skew and Redis connection timeout are configured rather than embedded policy
   thresholds. An accepted request returns 202; it means queued, not processed.

## Consequences and alternatives

- An idempotent 202-only protocol would permit repeated enqueue operations and
  provides no freshness check. The selected protocol rejects valid-window
  replays, subject to the cache limitation below.
- The Redis cache's replay reservations are volatile. Eviction, flush or restart
  can lose them before the window ends; fingerprint uniqueness still prevents
  duplicate stored alerts, but cannot prevent a repeated task publication.
  PB4 must choose and verify suitable Redis durability/eviction and operation;
  do not claim durable replay prevention before then.
- Failed or ambiguous publication consumes the event ID for the validity window.
  A sender must use a new signed ID for a retry; duplicate alert storage remains
  prevented by the worker's fingerprint constraint. No distributed exactly-once
  delivery is claimed.
- Timestamp freshness depends on reasonably synchronized clocks; configure and
  monitor the window rather than silently accepting stale traffic.
