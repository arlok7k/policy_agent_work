# DR-022 — Bounded scheduled login-throttle cleanup

- **Status:** Implementing follow-up PB2-PB4-FU01 in PB2 because the pinned
  Celery installation includes Beat. This resolves DR-007's PB1-era note that
  expired throttle rows had no cleanup. No additional migration or table grant
  is needed: migration 003 already grants the host runtime DELETE on the
  throttle table.
- **Eligibility and concurrency:** A batch may delete only rows whose
  `window_started_at` plus the configured login window is no later than a
  PostgreSQL `clock_timestamp()` sampled for that batch. Order by window start
  and digest, select at most the configured batch size with `FOR UPDATE SKIP
  LOCKED`, and delete those locked rows in the same transaction. Login's
  existing insert/upsert and row locks serialize with deletion. An active row or
  one currently being updated is never reset by cleanup; skipped rows can be
  reconsidered on a later run. The timestamp sample is conservative if the
  batch waits: rows expiring later are left for a subsequent run.
- **Schedule:** A registered Celery task runs on the default queue at a required
  operator-configured positive interval and removes at most a required positive
  batch size per invocation. Beat publishes the configured `service:` initiator
  header, and the same task-level initiator enforcement applies to direct and
  scheduled publications. Because result storage is disabled, disable Celery's
  otherwise automatic un-attributed backend-cleanup schedule. Run a single Beat
  process with a durable schedule file; duplicate Beat processes may cause
  additional bounded invocations, but row locking keeps cleanup safe.
- **Consistency requirement:** All web, worker and Beat deployments must use the
  same `LOGIN_WINDOW_SECONDS` and shared database. A shorter cleanup window than
  an API worker's window could erase that worker's still-active limit. Coordinate
  any window change across replicas; configuration drift is an operational risk.
  There is no claim of a global setting registry in PB2.
- **Failure and bounds:** Each invocation is one DB transaction; a failure
  rolls back the batch. No unbounded loop or application-clock expiry is used.
  The task returns only the deletion count and does not expose bucket digests.
  Cleanup is maintenance, not a security audit event. If Beat is stopped,
  expired rows accumulate but login still resets expired windows on access.
- **Alternatives:** Unconditional deletion, application-time expiry or a delete
  without row locks could erase a live throttle bucket. Sweeping the whole table
  in one transaction could overload the database. Redis-only cleanup would not
  govern the PostgreSQL rate-limit source of truth.
