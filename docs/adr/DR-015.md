# DR-015 — PB2 host data model and shared-tenant contract

- **Status:** Implementing PB2; the exact endpoint schemas and status codes will
  be published in `openapi.host.json` and the relevant subsequent DRs.
- **Owner selection:** In response to the PB2 contract question, the owner
  selected the option labelled **“Use the proposed contract”**. That option
  described UUIDs, a single shared tenant, access for every active legacy role,
  incident-scoped evidence, bounded inputs, configurable limits and keyset
  cursors. This is the literal option label, not a reconstructed quotation of a
  message. PB1's separately unconfirmed approval evidence remains unchanged.
- **Context:** §3.4 and PB2-T01 name host resources but leave their database and
  public wire contracts unspecified. The selected contract preserves the
  specified shared access; it does not invent per-user ownership or tenancy.

## Migration contract

1. Use UUID primary keys for alerts, incidents and evidence, matching the PB1
   host identifiers. Alert source, rule ID, severity and status are nonempty
   text; agent and source/destination IP are optional. IPs use PostgreSQL INET,
   the original payload is a JSONB object, and the 32-byte fingerprint is
   unique. A database timestamp supports stable cursor pagination.
2. Incidents have a nonempty title, optional description, status and timestamps.
   `incident_alerts` is a many-to-many association with a composite primary key.
   Investigation serializes on the alert when deciding whether to link or create;
   it does not infer ownership from a creator's identity.
3. Each evidence row belongs to one incident; an optional associated alert must
   actually be linked to that incident. The composite foreign key enforces this
   relationship, preventing cross-incident evidence references even if a caller
   supplies another incident's identifier. Evidence data is a JSONB object.
4. The IOC cache has a canonical indicator key, verdict, nullable score, JSONB
   sources, a mock marker, cache timestamp and expiry. Provider/cache policy and
   timeout handling are recorded separately before the endpoints rely on them.
5. Grant `hpb_app` only the operations needed by the PB2 routes and worker:
   read/insert/update alerts, incidents and IOC cache; read/insert associations
   and evidence. Do not extend activity-log mutation privileges. Downgrades drop
   only the PB2 tables, in dependency order, and are exercised only on a
   disposable database.

## Public boundary

All three active legacy user roles share the PB2 reads and permitted mutations
specified in §3.4; unknown or inactive principals are denied. A nonexistent
incident is not disclosed, and an evidence listing is scoped to the incident
in the URL. Because the baseline is single-tenant, another active legacy user
is not denied merely for knowing an existing incident ID. Incident creation uses
an explicit title, optional description and optional alert IDs. Lists use opaque
keyset cursors and configured bounds, not unbounded offsets. The webhook is a
separate HMAC service boundary; its replay protocol is recorded separately.

## Alternatives and consequences

- Per-user or tenant-scoped ownership would conflict with the specified shared
  legacy matrix and require an unrequested access model. A future requirement
  needs a new decision and characterization tests.
- Omitting the evidence-to-incident foreign key would leave cross-object
  consistency entirely to application code. The composite key prevents an
  evidence row from referencing an alert linked only to a different incident.
- The exact status vocabulary, field bounds and adapter outputs are baseline
  design choices, not facts quoted from the specification; document and test
  each before use.
