# DR-002 — PB1 development and verification boundary

- **Status:** Accepted for PB1.
- **Context:** The initial checkout has only reference documents and a
  one-heading root README. The session fixes its working branch name. PB1 is a
  backend-only phase, while several CI gates require components introduced in
  later phases. The sandbox initially has neither Docker nor PostgreSQL.
- **Decision:** Work on the session's fixed branch instead of creating the
  requested `phase/...` branch; open the PB1 PR from that branch to `main`.
  Add a PB1 GitHub Actions workflow now, on every pull request. Enforce the
  checks applicable to PB1; explicitly list later-phase gates as pending, never
  report them as passing. Use a disposable, isolated PostgreSQL 18.6 instance
  for migration and database tests, with no test data retained as an artifact.
  GitHub Actions uses its own disposable PostgreSQL service. No production
  credentials or data are required for tests. Dependency vulnerabilities are
  checked against PyPI; licenses are inventoried with unknown licenses failing,
  without inventing an owner licensing policy. All tracked files are secret-scanned.
- **Alternatives:** Deferring CI entirely to PB4 would conflict with the owner's
  every-PR instruction. SQLite would not test PostgreSQL triggers or privileges.
- **Consequences:** A passing PB1 workflow is not evidence that later governance
  gates or the PB4 Compose smoke test have passed. PB2 must not start before the
  PB1 PR is merged into `main`. The inventory includes LGPL-3.0-only psycopg
  packages; legal suitability requires owner review.
