# DR-048 — PB4 Compose data-service boundary on the Docker host

- **Status:** Open; owner decision required before treating AC-B4.3 as complete.
- **Context:** The Compose data network has `internal: true`, no published
  PostgreSQL or Redis ports, and the real smoke in
  [CI run 45632988120](https://github.com/arlok7k/policy_agent_work/actions/runs/45632988120)
  confirmed that an edge-only container could not connect to the actual data
  addresses while the backend could. It did **not** test connections originating
  from the Docker host. Docker [4](https://docs.docker.com/reference/cli/docker/network/create/)
  documents that an ordinary internal bridge normally has a host address and
  host processes can reach its container IPs, even without published ports. The
  actual GitHub runner's host reachability has not been measured. Both Redis
  instances are unauthenticated on this internal network. Local Docker is absent,
  so a real host probe needs CI or another disposable Docker environment.
- **Conflict:** AC-B4.3 says DB/Redis are unreachable from outside the Compose
  network. The prior test establishes edge-container isolation, not whether
  unprivileged host processes count as outside the intended boundary or are
  isolated from the data plane. Treating the entire Docker host as trusted is a
  consequential security assumption and must not be silently presented as
  proof of stronger isolation.
- **Options:**
  1. **Isolate the host (recommended):** require a compatible Docker Engine,
     use Docker's internal `isolated` gateway mode, add host-negative and
     internal-positive connection checks, retain the edge probe and exact
     Nginx trust, and rerun the unchanged end-to-end smoke. Docker Engine 28.0
     introduced the mode [1](https://github.com/moby/moby/releases/tag/v28.0.0).
     Docker administrators or host root can still change the network boundary;
     a pre-existing network must be recreated without deleting volumes.
  2. **Trust the Docker host:** explicitly treat all host processes as inside
     the security boundary and retain the edge-only network check. This does not
     demonstrate strict host isolation; AC-B4.3 and PR readiness require the
     owner's clarification of the acceptance boundary rather than an inferred
     approval.
  3. **Measure first:** add a non-destructive real-CI host connection probe and
     return with the result before choosing a network design. This leaves the
     acceptance decision open and requires another CI run.
- **Consequences:** No response safeguards or test assertions have been
  weakened. The complete browser smoke is green on the cited earlier commit,
  but final-head CI and PB4 baseline approval remain separate. Do not treat the
  host isolation requirement or the owner gate as passed by implication.
