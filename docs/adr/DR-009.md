# DR-009 — Proposed PB1 user and API-key endpoint details

- **Status:** Option A accepted by the owner before implementing PB1-T07 and
  T08. DR-006 approved the high-level boundaries; this record resolves the
  remaining wire-contract, key-transport and recovery details.
- **Context:** PB1 must provide admin user management, owned API keys and
  service-principal authentication. The guide names these routes without
  specifying their detailed wire contract.

## Recommended option A

1. **Users:** Only a currently active, cookie-authenticated `admin` may use
   `/api/users`. `GET` accepts optional `limit`/`offset` and returns
   `{items, limit, offset}`; server-configured defaults and maximum bound the
   page size. `POST` accepts exactly `{username, password, role}`, creates an
   active account, and returns its safe metadata with status 201. `PATCH`
   accepts `{id, password?, role?, is_active?}` with at least one change, and
   returns safe metadata with status 200. Metadata consists of `id`, `username`,
   `role`, `is_active`, `created_at` and `updated_at`; never a password/hash.
   Username is immutable, trimmed and lowercased, consists of ASCII letters,
   digits, `.`, `_`, `@` or `-` and starts with an alphanumeric character;
   maximum length is configured. Password length is configured as in DR-006.
   Role must exist in the database role catalogue. Duplicate names return 409,
   unknown IDs 404, and invalid semantic fields 422; malformed requests use 400.
2. **Revocation and lockout:** Password changes revoke every session belonging
   to the affected user. Disabling a user revokes all their sessions and owned
   API keys in the same transaction; re-enabling does not resurrect them.
   Role changes take effect immediately. An administrator may change their own
   password, but cannot disable or demote their own account (409); another
   administrator must do that. This preserves at least one active admin, given
   transactional identity/role rechecks and ordered user-row locks. An owner
   still needs a database-level recovery procedure for a lost last credential.
3. **API keys:** Only an active cookie-authenticated administrator may manage
   their own `/api/api-keys`. `GET` is paginated using the same page limits and
   returns safe metadata. `POST` accepts exactly `{name, ttl_seconds}`, where
   the nonblank name has a configured length bound and TTL is positive and no
   larger than the configured maximum; status 201 returns `{key, secret}` with
   `Cache-Control: no-store`. `key` contains `id`, `name`, `prefix`,
   `created_at`, `expires_at` and `revoked_at`. The `secret` is shown only once.
   `DELETE /api/api-keys?id=<uuid>` revokes an owned key and returns 204; a
   nonexistent or other owner's ID returns 404. Repeated revocation of an owned
   key is idempotent. Every mutation appends a safe `case_activities` entry in
   the same transaction.
4. **Key transport and identity:** The one-time token has a nonsecret random
   lookup prefix and an independent random secret; only a domain-separated
   keyed digest is stored. Clients send `Authorization: Bearer <secret>`.
   Database time, revocation and the owner's active status are checked on
   every use. `GET /api/auth/me` reports a valid key as a `service` principal
   with its key ID, no username, no roles and no reauthentication timestamp.
   API keys do not inherit their owner's role and cannot call user/key admin
   routes or use cookie-only logout/reauth. Mixed cookie and Authorization
   credentials are rejected rather than falling back.
5. **Race and rule handling:** Admin mutations lock and revalidate the actor's
   user/session and role in the same transaction as their writes; involved user
   rows are locked in a consistent order. Route allow-lists are declarative data
   derived from §3.4 and evaluated through the generic `require_roles` guard;
   no role hierarchy or client-provided role claim is trusted.
6. **Configuration:** In addition to DR-006's required settings, require
   `DEFAULT_PAGE_SIZE`, `MAX_PAGE_SIZE`, `USERNAME_MAX_CHARS`,
   `API_KEY_NAME_MAX_CHARS`, and `MAX_API_KEY_TTL_SECONDS`. The nonsecret
   `.env.example` values are 50, 100, 128, 128, and 2592000 respectively; these
   are operator-reviewed examples, not code defaults. No server starts if the
   required values are missing or inconsistent.

All requests reject unknown fields. Validation and database failures use generic
external messages without echoing input. The owner-approved RFC 9457 error and
correlation contract from DR-006 is implemented in T09; the health and dev-only
seed behavior remain as specified and do not require additional public APIs.

## Alternatives and consequences

- **A — Approve the recommended details:** PB1-T07 and T08 can proceed with the
  specified compatibility, concurrency, and last-admin protections.
- **B — Specify changes:** the affected tasks remain blocked until their exact
  security/public API contract is agreed; T01–T06 remain committed.
- **C — Pause:** retain the current branch and do not implement these APIs.

**Recommendation:** A. The details keep the approved admin-only and service
principal boundaries while making revocation and wire behavior testable.
