# DR-013 — Proposed PB1 health endpoint access

- **Status:** Option A accepted by the owner before PB1-T10 implementation.
  PB1-T10 names `/api/health`, and owner-approved DR-006 defines its minimal
  200/503 body, but did not explicitly resolve whether an unauthenticated caller
  may see database readiness. The §3.4 legacy table otherwise treats reads as
  authenticated, while infrastructure probes commonly run before login.

## Options

- **A — Public, minimal readiness (recommended):** `GET /api/health` requires
  no credentials, runs a database `SELECT 1`, returns only `{"status":"ok"}`
  on success, and otherwise a generic 503 problem. It reveals one bit of
  database readiness to anyone who can reach the API; network policy may further
  restrict access. Infrastructure probes do not need a session or key.
- **B — Authenticated readiness:** require an active cookie-authenticated
  user. Unauthenticated callers receive 401, reducing readiness exposure, but
  monitoring must securely obtain and maintain a user session; the health URL
  cannot diagnose database failure before authentication succeeds.
- **C — Other:** specify the desired access and response boundary; T10 remains
  blocked until clarified.

Both A and B omit credentials, configuration values and database error details;
readiness reports only database reachability, not future PB2+ dependencies.
