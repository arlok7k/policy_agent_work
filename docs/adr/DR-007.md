# DR-007 — PB1 authentication implementation details

- **Status:** Accepted by the implementation agent within the owner-approved
  boundaries in DR-006; subject to the later PB4 review.
- **Context:** PB1 requires secure cookie sessions, CSRF, step-up and login
  throttling, but leaves their implementation details open.
- **Decision:** Normalize usernames by trimming and lowercasing. Use Argon2id
  with the pinned argon2-cffi library's current defaults, including a randomly
  salted dummy hash for absent users, so absent and wrong-password checks use
  the same algorithm. Session and CSRF values are independent random tokens;
  persist only domain-separated HMAC-SHA-256 digests. A valid existing session
  may be rotated at login only with its CSRF token; an invalid/expired old
  cookie is ignored for public login. Mixed cookie and Authorization credentials
  are rejected. Cookie-authenticated unsafe methods are checked centrally.
- **Rate limiting:** Two PostgreSQL rows per login track failed attempts for the
  direct peer IP and normalized account. Their locks are acquired in digest
  order; DB time controls windows. A blocked request returns 429; invalid,
  missing and inactive accounts receive the same 401. Failed and throttled
  login activities use an anonymous actor instead of an untrusted username,
  which could contain a secret. Success does not erase failures within the
  current window. Limits are configured,
  not embedded in application code.
- **Step-up:** The password adapter accepts only the `password` assurance level,
  validates the active session/user and compares `reauth_at` to DB time and the
  caller-supplied maximum age. Unsupported levels and invalid ages deny.
- **Alternatives:** Per-process throttling is bypassable with multiple workers;
  a shared cache would introduce an additional dependency before PB4. Trusting
  forwarding headers before a proxy trust boundary is configured is unsafe.
- **Consequences:** Authentication mutations and their safe audit records are
  atomic. The default Argon2 cost is tied to the pinned library version and
  must be revisited deliberately if the dependency changes. Proxy deployments
  must configure trusted client IP handling before relying on source-IP quotas.
