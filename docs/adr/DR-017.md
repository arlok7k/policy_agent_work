# DR-017 — PB2 alert read contract and pagination

- **Status:** Implementing PB2-T04 under the shared-tenant contract selected in
  [DR-015](DR-015.md). Exact response schemas are exported in the host OpenAPI
  artifact at PB2-T09.
- **Context:** PB2 requires alert reads, filters, cursor pagination and a
  severity/status/24-hour summary, but does not specify their wire shapes or
  cursor ordering.
- **Decision:** All three active legacy roles may read all alerts. A missing ID
  produces 404; malformed IDs or cursors produce a generic 400. Alert views
  expose the UUID, source, rule ID, severity, optional agent and IPs, raw JSON,
  status and creation timestamp, not the internal fingerprint. Text and HTML
  are JSON data, never interpreted as markup. Responses are uncached and use
  `X-Content-Type-Options: nosniff`.
- **Filters:** Exact-match source, severity, status, agent and source/destination
  IP are optional; severity and status filters are normalized to lowercase.
  Text filters have the configured alert-field bound. The existing configured
  default and maximum page sizes apply.
- **Cursor:** Descending `(created_at, UUID)` keyset order, with a 24-byte
  timestamp/UUID position encoded as URL-safe base64. It is an opaque position,
  not an authorization credential or an encrypted value. A page contains
  `items` and nullable `next_cursor`; malformed tokens fail closed. This avoids
  offset drift and supplies a deterministic tie-breaker without an extra table.
- **Summary:** Return counts grouped by severity and by status plus a `last_24h`
  count computed against PostgreSQL's clock. Empty groups are empty objects.
- **Alternatives:** Offset pagination can repeat/skip records when new alerts
  arrive. Per-user filters conflict with §3.4's shared legacy role matrix.
