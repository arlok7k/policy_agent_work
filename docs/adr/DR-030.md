# DR-030 — Celery execution and durable recovery

- **Status:** PB3-T06; HTTP dispatch follows in PB3-T09.
- **Owner decisions (verbatim):**
  > - Four-Eyes = the approver must be a different user from the requester. L3 always needs approval
  >
  >   by senior_analyst or admin; the requester can never approve their own action.
  >
  > - Execution runs in a Celery task, not in the HTTP request. The task re-checks Safeguards and
  >
  >   the Kill Switch right before executing, and re-validates that the action is still approved.
  >
  > - Kill Switch halts AUTOMATION only (auto L1/L2 execution and TTL jobs); manual human-approved
  >
  >   execution stays possible. Engage/disengage by senior_analyst or admin, always audited.
- **Owner selections:** **“Fail terminally (recommended)”** for a now-ineligible
  approver or newly safeguarded target; **“Reconcile from database (recommended)”**
  for lost task publication or broker messages; **“Every 5 seconds
  (recommended)”** for the configurable, bounded response sweep cadence.

## Decision

Only a Celery task invokes the execution service. An HTTP request may persist
an action/decision and publish an execution message after commit, but never run
its connector. The database's `approved` row is the durable source of work;
a Beat task periodically finds up to 100 approved actions by default, executes
one short transaction per action, and retries outstanding work on later sweeps.
The interval and batch size are configurable. A switch-engaged scan skips
paused automatic actions so it does not starve human-approved actions. An
individual queued automatic task leaves its action `approved` when paused;
the next eligible sweep retries it. Availability depends on a live Beat, worker,
broker and database; the schedule is not an exactly-once or hard-latency claim.

The worker previews actor IDs, locks users in UUID order, locks the safety
snapshot, and then locks/rechecks the action. It requires the action still be
approved, validates catalog/level/mode and the current structured safeguards,
and reads the current switch immediately before the simulated command. For a
manual action it rechecks the immutable matching approval, distinct requester,
current active approver and current senior/admin role. For automation it checks
the requester is still active and eligible to request. Sessions are not carried
into the queue: the recorded approval is durable, while current user status and
role are checked at execution. Queue headers provide attribution only, not
authentication; the command's user identity is derived from the database.

Ineligible approval or requester, an invalid action, or a newly refused target
is audited and transitions to terminal `failed`, requiring a fresh request (and
approval where applicable). The Kill Switch instead pauses automatic work;
human-approved work is unaffected. A missing authorization policy, database or
audit failure aborts the transaction rather than executing; a later sweep can
retry. Command, `executing`/`executed` transitions, TTL timestamp, and their
activities commit atomically. Duplicate messages/sweeps serialize on the row;
only one command per action and phase is allowed. The L2 expiration is computed
from PostgreSQL's clock at the simulated command recording, not request or
approval time. Long-held locks may delay switch commits; the approximately
one-second propagation target is not a hard guarantee under database or queue
congestion.
