# DR-047 — PB4 migration commit granularity

- **Status:** Process deviation recorded for owner review; this is not baseline
  approval or a change to the database design.
- **Context:** The owner-authorized presentation settings use additive Alembic
  migration `009_host_settings`; [DR-036](DR-036.md) records the API and data
  boundary. Commit `4debaf5` contains that migration together with the PB4-T03
  implementation and tests. This met the one-task-per-commit convention but
  did **not** meet the additional §18.1 R-17 instruction that migrations have
  their own commits. The commit has already been pushed and later commits and
  CI evidence depend on it.
- **Decision:** Do not silently rewrite shared, already-pushed history or alter
  a migration solely to disguise the commit-granularity error. Report it in the
  PB4 Phase Report for owner review. Future migrations should be committed
  separately, as specified. This record does not waive R-17 or imply approval.
- **Verification and consequences:** The migration adds a host-only table; it
  does not alter pre-existing host tables. Disposable-database tests exercise
  upgrade, downgrade and re-upgrade, and the full backend suite passed with no
  IP routes. Those checks verify behavior, not compliance with the separate-
  commit process rule. The owner can request a reviewed history remedy if one is
  required; no persistent database should be rebuilt to address this issue.
