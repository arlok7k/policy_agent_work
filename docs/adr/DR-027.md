# DR-027 — Pure safeguards and synchronized safety facts

- **Status:** PB3-T03; read-only governance adapters may call the pure module.
- **Owner decisions (verbatim):**
  > - Execution runs in a Celery task, not in the HTTP request. The task re-checks Safeguards and
  >
  >   the Kill Switch right before executing, and re-validates that the action is still approved.
  >
  > - Kill Switch halts AUTOMATION only (auto L1/L2 execution and TTL jobs); manual human-approved
  >
  >   execution stays possible. Engage/disengage by senior_analyst or admin, always audited.
- **Owner selections:** **“Blocking and isolation only (recommended)”** and
  **“Refuse them too (recommended)”** were selected for IP scope and additional
  IPv6/special-address protection, respectively.

## Decision

`response/safeguards.py` is pure and exposes `check_safeguards(action)` with a
boolean and stable non-input-bearing refusal reason. It has no DB, clock,
network, logging or mutation side effects. It validates the catalog payload,
rejects nonnumeric/zero agent IDs (including leading-zero spellings of Agent
000), and inspects keys and values for shell metacharacters or controls using
Unicode NFKC for checking. User-provided text remains data; no command string is
constructed. Unknown actions, malformed payloads and malformed additional rules
fail closed.

For blocking or isolation, reject IPv4 RFC1918, loopback and link-local; IPv6
loopback and link-local; IPv6 unique-local; unspecified and multicast addresses
of both families. IPv4-mapped IPv6 is normalized before comparison. The pure
module retains these mandatory minimums and Agent 000 even if database facts
are accidentally removed; the seeded read-only rule table documents them and
can contain additive protected agents or CIDRs. IP policy does not prevent a
safe unblocking/release solely because the target IP is protected. However, an
independently requested L2 allow is checked against its future firewall-drop
reverse at request and execution time; unsafe automatic re-blocking is refused.
Rollback evaluates the actual reverse command, avoiding recursive TTLs.

The runtime reads the singleton switch row `FOR SHARE` and then snapshots the
rules in the same transaction. Switch toggles and rule insert/update/delete/
truncate take a conflicting row lock; a trigger on rule writes enforces the
latter even for the table owner. The execution transaction retains its lock
through the simulated command and activity write. Thus a rule or toggle that
commits first is observed, and a later change waits until the command completes.
This provides a serialization point, not the ability to undo a command that has
already started. PB3 still lacks a trusted agent/IP inventory; the safeguard
checks the structured simulated target supplied by the requester.
