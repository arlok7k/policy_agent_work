- **Owner request (verbatim):**

- **Owner selection:** The option **“Configurable, default 30 seconds (recommended)”**
  was selected. Its description was: “Return Retry-After: 30 unless the operator
  configures another positive delay; this is a retry hint, not a recovery guarantee.”

## Decision and consequences

The existing replay-store and publication failures already returned 503 in
`backend/app/alerts/webhook.py`, but the common problem handler discarded
`Retry-After`. Add the positive `WEBHOOK_RETRY_AFTER_SECONDS` setting with an
optional 30-second default. Both Redis replay-store failures and broker
publication failures return that delta-seconds header with the existing generic,
no-store RFC 9457 response. The shared problem handler forwards only an ASCII
decimal `Retry-After` on 503; other failures retain their prior behavior.

No replay reservation is created when the replay store cannot be reached before
reservation. However, a timeout can leave the reservation outcome ambiguous;
publication failures likewise retain a reservation because delivery might have
succeeded. A sender retry must account for 409 replay rejection and may need a
newly signed event ID; the hint does not guarantee recovery or exactly-once
delivery. The existing fingerprint deduplication and Redis durability limits
in [DR-016](DR-016.md) remain unchanged. The new header is documented in the
host OpenAPI contract and tested with an actually unreachable Unix socket as
well as simulated dependency failures.
