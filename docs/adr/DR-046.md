# DR-046 — PB4 worker bootstrap for complete ORM metadata

- **Status:** Implemented; the executed-command stage passed in real Compose.
  The complete Compose smoke still needs to pass.
- **Context:** [CI run 45272060611](https://github.com/arlok7k/policy_agent_work/actions/runs/45272060611)
  started the Compose stack and passed the backend and frontend jobs, but its
  Playwright smoke timed out after an L3 approval with no matching executed
  command. The CI worker log could not be downloaded from this sandbox.
- A separate disposable local reproduction used PostgreSQL 18.6, Redis 8.2.11,
  Python 3.15.2, the pinned application dependencies, Gunicorn, and a standalone
  prefork Celery worker. The same approval-to-command observation failed: the
  action remained `approved`, and the worker reported `NoReferencedTableError`
  for `response_actions.incident_id` because the `incidents` model was absent
  from its process's SQLAlchemy metadata. Beat reconciliation reported errors.
  A fresh-process regression confirms the incident mapping is absent when the
  original CLI entrypoint is imported alone. In-process tests import the API
  and incident models first and therefore do not expose this startup condition.
  The local finding does not establish what the inaccessible CI log contained.
- **Decision:** The owner selected **“PB4-only bootstrap (recommended)”**.
  Provide a PB4 deployment entrypoint that registers the existing incident
  mapping before exposing the unchanged Celery app. Use that entrypoint for the
  Compose worker, Beat and their health probes, and document it for standalone
  operation. Add fresh-interpreter metadata and separate real-worker regression
  tests. No PB3 response state machine, safeguard, connector, authorization,
  migration or database privilege is changed. The fresh-process mapping test
  and a separate prefork worker's direct-execution and reconciliation regression
  passed. The unchanged local HTTP/worker reproduction then succeeded, and Beat
  recovered the action left approved by the earlier failed reproduction. The
  full no-IP backend gate passed 387 tests, Ruff, formatting, mypy and OpenAPI.
  In [CI run 45631218996](https://github.com/arlok7k/policy_agent_work/actions/runs/45631218996)
  the unchanged Compose smoke passed the approval-to-command assertions, then
  failed at a separate modal focus assertion; see PB4-FU05 in progress.
- **Alternatives:** Change the existing PB3 `app.jobs.worker` entrypoint, which
  was outside the selected scope; hide the smoke failure; import the entire API
  application solely for its incidental model imports; or weaken database
  constraints. The latter three would obscure the defect or its boundaries.
- **Consequences:** The original direct PB3 CLI entrypoint remains unchanged and
  must not be used as a standalone deployment command; use the documented PB4
  entrypoint instead. Rebuild and restart workers after rollout so registered
  mappings take effect. Existing approved work remains durable and can be
  retried by the existing bounded reconciliation when the corrected worker and
  Beat are healthy. A successful local reproduction is not the required real
  Compose Playwright result, and PR readiness is not baseline approval.
