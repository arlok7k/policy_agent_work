# DR-012 — PB1 problem responses and safe request logging

- **Status:** Accepted by the implementation agent, implementing the DR-006
  error and correlation contract and spec §14.3; DR-006 owner approval remains
  to be confirmed.
- **Decision:** Typed host errors and framework validation/HTTP errors are
  mapped centrally to `application/problem+json` with `about:blank`, a generic
  standard HTTP title, matching status, a `GOV-HTTP-<status>` code following
  §17, and the request correlation ID. Validation details, exception
  text and submitted values are never returned. Safe caller IDs must be
  canonical UUIDv4 strings; otherwise the service generates a UUIDv4. Each
  response carries `X-Correlation-Id`. The current ID is included in host
  activity `details` without changing the append-only schema.
- **Logging:** The application emits one allow-listed JSON request event with
  UTC time, severity, component, correlation ID, principal kind, HMAC-hashed
  principal ID, route template, outcome and status. It never logs request
  bodies, headers, query strings, raw principal IDs, credential digests or
  exception messages. Unknown exceptions are logged by class only and return a
  generic 500; database/security failure statuses remain fail closed.
- **Consequences:** Invalid incoming IDs are replaced rather than echoed. Route
  templates—not user-controlled paths—are logged. Deployments must disable
  server/proxy access logs that include raw URLs, headers or request bodies,
  and must not enable SQLAlchemy parameter/statement logging. Celery context
  propagation is deferred to the phase that introduces Celery (PB2).
