# DR-023 — Host OpenAPI contract and isolated PB2 CI

- **Status:** Implemented locally for PB2-T09; final-head CI is tracked in the
  PR checks and owner review remains pending. This describes the actual PB1/PB2
  host surface only; it does not claim the PB3 response or later governance APIs.
- **OpenAPI:** Commit a deterministic OpenAPI 3.1 export at
  `openapi.host.json`, generated from the registered FastAPI application, and
  check it for drift. Preserve typed success bodies while documenting generic
  RFC 9457 `application/problem+json` failures with the actual status codes.
  Validation failures are 400, not FastAPI's default 422 schema; 422 is
  reserved for host semantic limits. Document user-cookie, double-submit CSRF,
  service-key and webhook-HMAC boundaries and attach legacy operation/role
  metadata. The always-present `mock=true` and webhook `accepted=true` markers
  are required literal fields in the response schemas; constructors now set
  them explicitly without changing the wire responses. Dynamic bounds are
  described by configuration name, not falsely encoded as fixed schema maxima.
  The full API inventory and role behavior are
  characterized by [DR-021](DR-021.md).
- **Contract verification:** `jsonschema==4.26.0` and
  `openapi-spec-validator==0.9.0` are development-only, hash-locked tools.
  Validate the exported specification and exercise real successful and error
  responses against its schemas. Schema validation is not a substitute for the
  dedicated security, role, replay and concurrency tests.
- **CI network boundary:** PostgreSQL 18.6 and two separate Redis 8.2.11 service
  containers are disposable. Before running `make check`, a local-only bridge
  exposes those three services as Unix sockets. The test subprocess runs in a
  fresh Linux network namespace with its IP interfaces down, verifies that
  neither loopback nor external IP routing is available, and receives only the
  Unix socket paths. Thus tests can use PostgreSQL and both Redis instances but
  cannot directly reach external providers; application startup installs only
  the deterministic mocks. Dependency installation/auditing runs outside that
  namespace because those steps need package/vulnerability metadata.
- **Alternatives and limitations:** Simply mocking HTTP calls does not prevent a
  newly added provider from opening a socket. Blocking only DNS or a handful of
  domains is not a network-disable guarantee. The bridge itself runs outside
  the namespace and connects only to the three configured loopback service
  ports; it is test infrastructure, not an application proxy. GitHub service
  containers and explicit `CI_DISPOSABLE_SERVICES=1` confirmation remain
  required; the flag does not make a shared service disposable.
