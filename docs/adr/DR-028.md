# DR-028 — PB3 approval gate and lifecycle

- **Status:** PB3-T04; the execution worker and HTTP wrappers follow in later
  PB3 tasks. This is not the later Governance Plane approval workflow.
- **Owner decisions (verbatim):**
  > - Four-Eyes = the approver must be a different user from the requester. L3 always needs approval
  >
  >   by senior_analyst or admin; the requester can never approve their own action.
  >
  > - Execution runs in a Celery task, not in the HTTP request. The task re-checks Safeguards and
  >
  >   the Kill Switch right before executing, and re-validates that the action is still approved.
  >
  > - Kill Switch halts AUTOMATION only (auto L1/L2 execution and TTL jobs); manual human-approved
  >
  >   execution stays possible. Engage/disengage by senior_analyst or admin, always audited.
- **Owner selection:** **“No expiry in PB3 (recommended)”** was selected for
  pending and approved decisions. `expired` remains a reserved lifecycle state,
  not an implicit deadline. Indefinite approvals are an open PB4 review risk.

## Decision

An action starts `requested`. L0 advances to `advised` without execution; L1 and
explicit automatic L2 advance to `approved` as a system eligibility state;
manual L2 and all L3 advance to `pending_approval`. Only an active, current
session with a role allowed by the versioned legacy policy may approve or
reject. An approver is always distinct from the requester, including for manual
L2; the requester may reject their own pending action if otherwise eligible.
One recorded decision per action, row locking and the database trigger prevent
double decisions and self-approval. Missing IDs return 404, illegal transitions
409 and self-approval 403. These are designed wire/status choices.

A decision reason is optional; if supplied, it must be nonempty valid UTF-8 and
within the configured text bound. It is stored as data in the decision record,
not copied into activity details or command arguments. The transition helper and
decision record share a transaction with the existing append-only
`case_activities` writer. An audit failure rolls back the decision.
A valid manual decision may be made while the Kill Switch is engaged; no command
runs in the gate or HTTP request. The future task must independently re-read the
switch and rules and verify the decision, current active approver and role at
execution. The `approved` state of automatic actions is *not* a human approval.
Every later edge is audited with only status, level and action ID, not input
parameters or reason text. Database constraints provide defense in depth but do
not authenticate a database user or replace the live application role check.
