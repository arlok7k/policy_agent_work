# DR-026 — PB3 action catalog and structured payloads

- **Status:** PB3-T02; the owner will review the complete baseline at PB4.
- **Owner decisions (verbatim):**
  > - L2 actions have a mandatory TTL with automatic rollback by Celery Beat. Make the default TTL
  >
  >   and its maximum configurable, with safe defaults you propose in a DR.
  >
  > - Connectors are simulated: they write to executed_commands and NEVER perform network I/O.
  >
  >   Add a socket-level test proving no connection is attempted.
- **Owner selections:** **“Strict structured targets (recommended)”**,
  **“Explicit automatic or approval mode (recommended)”**, and **“Make
  release_host rollback-only (recommended)”** were selected. See DR-025 for the
  other verbatim owner decisions and schema context.

## Decision

Publish the immutable catalog through `GET /api/response/catalog`, available to
all active §3.4 roles. It supplies the level, connector, reversibility,
requestability, allowed execution modes, TTL requirement, reverse action, and
JSON Schemas for targets and parameters. One definition supplies both the
published schema and the validator used for requests; extra properties are
forbidden. Catalog entries and field shapes are implementation choices, not
additional facts from the guide.

- L0 `advisory` accepts a `target.value` and `params.message` and never executes.
- L1 `ioc_add`, `ioc_update`, `fp_mute`, `escalate`, and `notify` use the
  simulated internal connector and execute automatically. Their `target.value`
  names the indicator, rule, escalation destination, or notification recipient.
  `escalate` and `notify` have a `message` parameter; the other three take an
  empty parameter object. The simulation records intent, not a real IOC update,
  mute, escalation, or notification.
- Independently requestable L2 `firewall_drop` and `firewall_allow` take a
  `target.agent_id` and `target.ip` and an empty parameter object. They reverse
  one another, require a bounded TTL, and support explicit automatic or manual
  approval mode. The reverse must also pass the applicable Safeguards.
- `release_host` remains an L2 catalog operation but is **rollback-only** for
  an existing isolation; it cannot be independently requested. Thus its reverse
  does not automatically execute the L3 `isolate_host` command without an L3
  approval. Reverse commands are not independent L2 actions with recursive TTLs.
- L3 `isolate_host` takes `agent_id` and `ip`; an authorized manual rollback
  uses `release_host`. `permanent_block` takes `agent_id` and `ip`,
  has no automatic TTL and has no PB3 rollback. Both require manual Four-Eyes
  approval; the permanent block is represented by a simulated firewall-drop
  command, not a real network call.

Schemas make required fields explicit, but runtime configuration will bound text
sizes. Safeguards additionally reject Agent 000, protected blocking targets and
metacharacters; schema validation alone is not a security substitute. PB3 has
no trusted agent-inventory/address binding, so it checks the supplied simulated
target and does not claim to verify an agent's real network addresses. The
catalog has no real connector, governance data or side effects.
