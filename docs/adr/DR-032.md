# DR-032 — Audited, automation-only Kill Switch

- **Status:** PB3-T08.
- **Owner decision (verbatim):**
  > - Kill Switch halts AUTOMATION only (auto L1/L2 execution and TTL jobs); manual human-approved
  >
  >   execution stays possible. Engage/disengage by senior_analyst or admin, always audited.
- **Owner selection:** **“Succeed and audit every call (recommended)”** for a
  repeated request that sets the switch to its existing value.

## Decision

`POST /api/response/kill-switch` accepts only an explicit JSON boolean
`engaged` and returns the committed state, actor ID and database timestamp. It
requires a live CSRF-protected senior/admin cookie session and revalidates that
actor under a user lock in the write transaction. Every authorized call,
including a no-change reaffirmation, updates attribution and appends a
`response.kill_switch` activity with before/after values. An audit or database
failure rolls the write back. This is not a governance switch or a frontend.

The switch row is locked for update by the endpoint. Execution and rollback
workers hold a conflicting share lock while reading the switch, snapshotting
safeguard facts, recording commands and auditing transitions. A toggle that
commits first is therefore observed by the next task; a toggle racing an
already-started command waits for it to commit, not retroactively undo it.
Automatic L1/L2 execution and TTL rollback pause; approved manual execution
(and authorized manual rollback when implemented) remains possible. Overdue or
paused automatic work is recovered by the bounded Beat sweeps after release.
A real running-worker regression changes the switch without restarting the
worker and checks both paused automation and permitted manual execution.
The approximately one-second target depends on DB/queue responsiveness and is
not a hard guarantee when a transaction is already in flight or overloaded.
