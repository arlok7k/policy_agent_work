# DR-040 — Explicit development-only HTTP cookies (PB4-FU02)

- **Status:** Implemented and exercised in the real Compose browser smoke;
  subject to the PB4 baseline gate.
- **Context:** The secure `__Host-` cookies cannot be used over ordinary HTTP.
  The owner selected **“Explicit dev-only opt-in (recommended)”** with separate
  names and a production rejection of the flag.
- **Decision:** The default remains the unchanged Secure, host-only,
  `__Host-soc_session` and `__Host-soc_csrf` pair. Only `ENV=development` with
  `DEV_INSECURE_COOKIES=true` selects non-Secure `soc_dev_session` and
  `soc_dev_csrf` cookies. The only accepted explicit values are lowercase
  `true` and `false`; the presence of this flag at all in test or production
  configuration fails startup. Both modes preserve host-only path `/`, Strict
  SameSite, an HttpOnly session cookie and session-bound double-submit CSRF.
  The server reads only the selected namespace. Dev session token digests use a
  separate purpose, preventing replay as production sessions even if a signing
  secret and database were accidentally shared. Production digest semantics
  and OpenAPI's production cookie contract remain unchanged.
- **Reason:** Local HTTP works only through an explicit, visible opt-in; an
  insecure test/development flag cannot silently weaken production.
- **Alternatives:** Remove Secure from production cookies, or permit a generic
  deployment toggle in all environments; both undermine the production boundary.
- **Consequences:** Development HTTP sessions are sent in cleartext; use only a
  trusted local environment with throwaway secrets and data, never production.
  Use different hostnames for production and development, so both CSRF cookie
  namespaces cannot conflict. Production remains HTTPS-only and needs operator
  TLS. The Compose HTTP smoke checked the development cookie attributes in CI
  run 45632988120; production Secure-cookie behavior is covered by backend
  tests, not by that HTTP-only browser run.
