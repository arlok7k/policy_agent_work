## Decision

Migrations 006–008 add only the five PB3 tables; they do not alter PB1/PB2
schema. Each independently requested action references an existing shared-tenant
incident and user, holds a JSON object target and parameters, and has an
immutable request, level, mode and TTL duration. A database trigger checks initial
state, permitted state transitions and immutability; the service will add an
activity event for each transition. `advised` is an added terminal status for L0
so an advisory is not misleadingly described as an executed command. `expired`
is reserved for expiry, not a synonym for TTL rollback.

L0 is advisory, L1 automatic, L2 explicitly automatic or manual with a positive
TTL, and L3 manual. A manual action cannot reach approved/executing/executed or
rolled-back states without a distinct recorded approver. Rejections may be made
by the requester if they hold the required senior/admin role; the owner forbids
self-**approval**, not self-rejection. PostgreSQL independently rejects
self-approval, requires a matching decision for manual state transitions,
serializes a decision on its action, and permits only one decision per action in
addition to the specified unique action/approver pair. The application must still
check live role, active status, session and other safeguards: database actor IDs
are not authentication.

`executed_commands` records structured simulated commands rather than shell
strings, with a unique `(action_id, phase)` so task redelivery cannot append a
second execution or rollback. Both command and decision logs are append-only,
including an owner-visible trigger and runtime privilege restrictions. A manual
rollback request is recorded on its original action and may be superseded by a
newly authorized human while the action remains executed, so revocation or a
lost task cannot permanently block recovery. A worker must match the current
request before executing it. A reverse command is not another independently
requested L2 action and does not recursively acquire a TTL. `rollback_of_id`
is retained for the specified schema but is not used to
create a new action in this phase.

The switch has one preseeded row, protected against deletion, and must be read
in each task. Its runtime identity can read/update but cannot create or delete
rows. Safeguard facts are seeded and runtime-read-only; additions are possible by
the migration/operations owner, not through a PB3 API. The pure evaluator will
always retain the mandatory baseline independent of those rows; additive rules
can make a target newly safeguarded after approval. A malformed rule fails closed.
Network and shell details, transactional lock ordering, TTL scheduling and API
shapes are recorded in subsequent PB3 DRs before use.

## Consequences

Each migration has a destructive down-migration for disposable databases only.
The shared-tenant model does not invent per-user incident ownership; unauthorized
principals and nonexistent IDs must still fail without disclosure. A poisoned or
misconfigured broker is outside these database invariants, and the PB2 initiator
header is attribution rather than an authenticated authorization proof.
